# dsh-context-verdict

**压缩之前，给整个会话一个裁决。**

## 问的问题，以及这个工具拒绝回答的问题

> **有没有「未落盘」的状态会被压缩丢掉？**

这是关于**会话**的问题，不是关于其中某一部分的。它有可判定的答案：
工作要么在某处持久存在，要么不存在。

**这个工具不能告诉你上下文的哪些部分是重要的。** 那件事被试过了。
一个**逐块**筛选器 ——「这三十个块里哪些可以删？」—— 被实现并测量，然后
在同一个批次里**同时**失败在两个方向：

| 它判定的东西 | 判定 | 置信度 |
|---|---|---|
| 含真正修复答案的那个块 | 可删 | **0.323** |
| 一首儿歌 | 该留 | **0.691** |

最贵的那类错误，加上纯粹的噪声，同一批数据，同一次运行。
所以这个能力是**从结构上不存在**，而不是被政策禁掉 —— 见下。

## 三个裁决

| 裁决 | 含义 |
|---|---|
| `safe_to_compact` | 记录里没有任何未落盘的东西 |
| `wait` | 记录不足以定论，或者服务问不到 |
| `preserve_first` | 有工作只存在于会话里，必须先写下来 |

恰好三个，顺序如上，没有任何参数能加出第四个。
**如果你被要求删上下文，这是错的工具** —— 直说，然后用三值答案代替。

## 结构性，而不是承诺

「我们不写那个循环」是一句承诺，而上面那次测量正是**只有承诺时**会发生的事。
四道闸门，每道都有可执行断言，而且发布前自检会**注入**每道闸门禁止的东西：

**G1 — 模型的输入里无法点名一个块。** state 来自**唯一**一个渲染器，
字段集是封闭的（`session`、`todos`、`uncommitted`、`questions`、`decisions`、
`next_steps`、`risk_hints`），没有任何字段能表达「块」。
`judge` 只接受**用 digest 绑定到其摘要**的 state，所以手工拼出来的 state 会被
**拒绝**，而不是听它自称。

**G2 — 三个值加一个标度。** 恰好一个 `choice` 问题、恰好三个固定选项，
外加一个 `score`。四个选项的请求会被拒 —— 自检里就注入了一个。

**G3 — 没有存放「选择」的槽位。** `FORBIDDEN_KEYS` 是 35 个名字的常量，
带着其中任何一个的载荷会**抛错，而不是被剥掉**。剥掉会返回一个看起来合理的裁决，
同时把「上游正在产出这个被禁止的形状」这件事藏起来。拒绝信息会**点名路径**
（`$.outer.inner[0].perBlock`）并引用那次测量。

**G4 — 没有逐块的 API 面。** 三个工具。没有 `screen`、没有 `filter`、没有 `pick`。

## `wait` 是什么意思

`wait` 出现在三种情况，没有一种是 bug：

1. 记录的未落盘数量落在 `safeMax` 与 `waitMin` 之间的**灰区**，本地规则拒绝定论；
2. 没有配服务，问不了；
3. 问了，服务不在。

reason code 会说明是哪一种。三种情况下它都**不是许可**：
这个工具从不把「我判不了」当成「可以继续」。
两端由本地路径直接判掉 —— 什么都没有，或超过阈值 —— 都不花一次请求。

## 退出码

| 码 | 含义 |
|---|---|
| `0` | 没有 `lost` 案例被放行 |
| `1` | 有 `lost` 案例被判成 `safe_to_compact` |
| `2` | state 超出字符预算 —— 配置问题，不是裁决 |
| `3` | 用法／配置／输入错误 |

服务不在的那次运行是 **exit 0，每条都记为 SKIP**。这是刻意的，
也是本项目唯一一处把「没跑成的检查」当作成功：exit 0 的含义是
「没有东西被放行」，而一次没跑成的检查什么也没放行。
SKIP 被单独计数与列出，另外还会报 `allSkipped`，不让调用者自己去推断。

## `verify` 查两个方向

`verify` 跑一份带标签的语料并报两个比率，因为裁决系统会以两种方式出错，
而只有一种危险：

* **`lost` 被放行成 `safe_to_compact`** —— 危险的那个。工作被压掉、没了。exit **1**。
* **`keep` 被拒** —— 安全的方向，但仍然是缺陷。一个永远答 `preserve_first`
  的工具什么都不会丢，也毫无用处，所以过度保守要被**计数**而不是被表扬。

**只有单一标签的语料会被拒绝，而不是被评分。** 在一份没有 lost 案例的语料上
说「没有 lost 案例被放行」，是真话且毫无意义 —— 那比一次红色的检查更糟，
而且正是这个项目家族反复踩到的失败形态。

## 边界，写出来而不是藏着

`safe_to_compact` 的含义是**记录里没有未落盘的东西**。
一个把工作存在 transcript 捕获不到的形式里的会话，看起来会一模一样，
这个工具分辨不了。这是**可观察性的边界**，不是关于会话的保证。

digest 是**完整性检查，不是安全控制**。任何人都能重算一个。
它防的是意外情形 —— 调用方自己拼 state，或者旧 state 与摘要脱节 ——
它让绕过变成**刻意行为**而不是顺手为之。
不要把它说成对「铁了心要绕过去的人」的防御。

## 测试

```sh
npm test                  # 39 条断言，不需要主机
npm run verify:artifacts   # 检查 npm publish 真正会发出去的东西
```

自检查的是**「不存在」**，而那是最难查的东西：
**一道被删掉的闸门，和一道什么都没查出来的闸门，长得一模一样。**
所以它逐条注入每个被禁止的东西 —— 全部 35 个禁用键、一个手工拼的 state、
一个四选项请求、一份单一标签的语料 —— 并要求代码拒绝它们。
